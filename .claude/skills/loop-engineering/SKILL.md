# ループエンジニアリング

**この型は1つのリポジトリの飾りではない。** 既にジョイ・リリーフ・ステーション（卵商店街）と
たまご進捗工場（tamago-shinchoku）という、仕組みも言語も別のプロジェクトで実際に動いている
（下記「実装例」参照）。**汎用スキルとして切り出す＝複数の現場で同じ型が成立することを確認する**
ということであり、本ファイルはその切り出し作業の成果物そのもの。

## これは何のためにあるか

**人間が同じ説明を二度三度しないで済むようにするための型。**

AIとの作業は会話単位で切れる。会話が切れるたびに、人間が背景・経緯・決定事項・
残件を喋り直すことになる。これは人間の時間を最も大きく削る無駄であり、
**回数を重ねるほど悪化する**（説明が増え、記憶違いが混ざり、やり直しが起きる）。

解決は単純で、**状態を会話ではなくファイルに置く**こと。
そして「読む」「回す」「書き戻す」を毎回の型にすること。

> 単発の指示文を磨いて終わりにしない。ゴールまで自律的に回る、
> 安全で検証可能なループを設計する。人間は毎工程の作業者ではなく、
> ゴール・制約・最終判断を持つ **Human on the Loop**。

もう一つ、同じくらい重要な前提がある。**「完了しました」という自己申告は完了の証拠ではない。**
AIは自分の仕事を甘く判定する傾向から逃れられない。だからこの型は「書き戻す」だけでなく、
**完了を機械の検品（exit code・URL実測・件数照合）に決めさせる**ところまでをワンセットにする。

## 3つの部品（これだけ）

| | 中身 | 更新頻度 | 例 |
|---|---|---|---|
| **① 担当台帳** | 担当ごとの**恒久情報**：呼び名のゆれ／使命／読むもの／触る場所／触ってはいけない場所／過去に落ちた穴／検品の仕方／完成条件 | 事故や方針が増えた時 | `roles.json`、`ROLES.md` |
| **② 現在地メモ** | 担当ごとの**今の状態**：今の方針／直近の決定／次にやること | 作業のたび | `playbooks/<担当名>.md`、`genzaichi.md` |
| **③ 見張り** | ①②が現物とズレていないか、完了申告が本当に完了しているかを**機械で**確かめるもの | 自動（起動時・CI・一定周期） | `role:check` 相当、`kenpin_gate.py`、`oni_modoshi.py` |

**①と②を混ぜない。** 恒久ルールを現在地メモに複製すると、両方が古くなって食い違う。
現在地メモには1行ポインタだけ置き、本文は台帳・正式ドキュメント側に置く。

**③を必ず作る。** 人間が読む文書は放っておくと必ず現物とズレる。
ズレたまま次のセッションが読むと、人間がまた説明をやり直すことになり、目的そのものが壊れる。
**文書を作る側と、腐りを見張る側は、必ず対で用意する。**

## 毎回の型

### Phase 1 — 読む（着手前・省略不可）

1. 依頼の言葉から**担当を1つ特定する**（迷ったら一番近い担当。落とし穴はだいたい共通なので、読まずに始めるより必ず良い）。
2. その担当の**台帳と現在地メモを読む**。
3. 現在地メモが無い／古い場合、**「進捗ゼロ」と決めつけない。「現在地が未確認」**として扱い、
   最新の本流（main）・直近コミット・作業ブランチ・進行中作業ボード・キュー台帳から実態を確かめる。
4. **人間に経緯を聞かない。** 聞く前に、自分で調べられる場所を全部見る。

### Phase 2 — 決める（内部で固定する）

着手前に、口に出さなくてよいので次を確定させる。

- 目的 ／ 完成条件（Definition of Done）
- **どうやって合格を確かめるか**（検証手段。できれば exit code か URL 実測）
- 変更してはいけない範囲
- 試行回数・時間・コストの上限
- 人間へ上げる条件（＝それ以外では止まらない、という宣言）

### Phase 3 — 回す

**Act → Verify → Refine** を、完成条件を満たすまで自分で回す。

- **Act**：安全に完成した分は小分けで保存する。全部できてから出そうとしない。
- **Verify**：**自分の「できたと思う」を合格にしない。** 外部の証拠で決める。
  - コード：型・テスト・ビルド・実際の画面
  - データ：件数・重複・欠損・サンプル照合
  - 調査：一次情報・複数根拠・日付
  - 公開物：**本流への到達・公開URLでの実測（HTTP 200 かつ本文が空でないこと）**
  - 確かめられなかった項目は「合格」と書かず、**未検証として残す**。
- **Refine**：失敗したら、表面的な回避ではなく原因を特定する。
  **同じ原因で2回失敗したら、同じ手段の繰り返しをやめて別経路へ切り替える。**

### Phase 4 — 書き戻す（ここを飛ばすと仕組みが死ぬ）

終わる前に、必ず3つ。**これが本体。**

1. **現在地メモの「次にやること」を、今の状態に書き換える。**
2. 進行中作業ボード・キュー台帳の自分の行を更新または削除する（複数セッションが同時に動く場合）。
3. **新しく分かった落とし穴・恒久ルールを、台帳に1行足す。**

3を足さないと、次のセッションが同じ失敗をして、人間がまた同じ指摘をすることになる。
**この1行を足す作業が、ループエンジニアリングの正味の価値。**

### Phase 5 — 止める

次のどれかで止める。それ以外では止まらない。

- 完成条件と検証を両方満たした
- 本人しか突破できない壁に当たった（本人認証・新しい鍵・権限・課金・法的承認）
- 事前に決めた試行・時間・コストの上限に達した
- 続けると既存資産を壊す危険が増える

**上限到達は「完了」ではない。** 安全な成果を保存し、唯一のブロッカー・試した経路・
次の再開点を現在地メモへ書いてから止める。

## Builder / Judge / Manager を物理的に分ける

**前提：同じ推論プロセスは同じ盲点に陥る。** 自分が書いたものを自分で読み返しても間違いは見つからない
（見つかるなら最初から書いていない）。だから**役割を分ける**。気持ちの問題ではなく、配線の問題。

| 役割 | 仕事 | やってはいけないこと |
|---|---|---|
| **Builder（構築者）** | 第一稿を作ることに専念 | 自分で自分に合格を出す |
| **Judge（判定者）** | **外部の正解データ**と突き合わせてPASS/FAILを出す | 印象で語る／自分で直す |
| **Manager（管理者）** | 次の一手だけ決める（納品／差し戻し／エスカレーション） | 気を利かせて上限を超える |

### Builderの出力は必ず構造化する

```json
{
  "deliverable": "何をやったか（言葉）",
  "confidence_score": 0.9,
  "uncertainties": ["自分でも確信が持てていないところ"],
  "assumptions": ["前提として置いたもの。外れたらここを疑う"],
  "evidence": ["Judgeが実際に走らせる検証手順"]
}
```

**`evidence` が肝。** 結論だけでなく「その結論を機械が確かめる手順」を必ず添えさせる。
**`confidence_score` が高いことは正しさの証明にならない**（むしろ 0.9以上で `uncertainties` が空なら過信のサイン）。

### Judgeには「外部の正解データ」を持たせる

**Builderと同じ情報しか持たないJudgeは機能しない。** ドメインごとに、頭の外にある正解を用意する。

| ドメイン | 正解データ |
|---|---|
| コード | テスト・型チェック・ビルド・静的解析の**終了コード** |
| データ | 生データの再集計（件数・欠損・重複） |
| 事実 | 一次情報・公式API・本番DBの実スキーマ |
| 公開物 | 本番URLの中身・`origin/main` の祖先判定 |

**Judgeは主張の文章を読まない。** 読むと同じ推論に引きずられる。読むのは `evidence` の手順だけ。
出力は `PASS` / `FAIL` と、FAILなら「どの証拠が」「どう失敗したか」。**「良さそう」は出力に存在しない。**

**証拠0件の主張は自動でFAIL。** ここを緩めると全部が自己申告に戻る。

### Managerは純粋ロジック

```
PASS                  → 納品。もう触らない
FAIL かつ 試行 < 上限 → Builderへ差し戻し（Judgeの指摘をそのまま渡す）
FAIL かつ 試行 ≧ 上限 → 人間へエスカレーション
```

上限は3〜5回。**「あと1回だけ」を許すとコストが青天井になる。**
エスカレーション時は必ず**「どこまで試して、何が原因で詰まったか」**と、Builderが置いた**前提**を添える
（前提が外れているのが原因のことが多い）。

### もう1層：横相談（Peer Help）を Manager の手前に置く

Builder / Judge / Manager だけだと、**専門外で詰まった時に行き先が「人間」しかない。**
人間が「それは別の担当の話」と振り分けるだけの伝書鳩になり、いちばん時間を溶かす。

そこで**エスカレーションの一つ手前**に、担当同士が直接助けを求める層を置く。

```
詰まる → ①自己解決を2〜3手 → ②横相談（隣の担当へ） → ③人へエスカレーション
```

助けてカードの型（そのまま使える）：

```yaml
task: login-recovery-018
from: browser-agent
problem: ログイン後に白画面
observed: [auth success, route transition success, render failure]
tried: [reload, cache clear, session refresh]
hypothesis: [client state hydration]
need: React / frontend specialist
urgency: high
```

**運用で効かせるための3つの縛り：**

1. **`tried` が空のカードは受け付けない。** 横相談は自己解決の後であって、代わりではない。
2. **`need` が実在する担当でなければ受け付けない。** 宛先の無いカードは永遠に拾われない。
3. **自分宛のカードは、自分の残件より優先する。** 誰かが自分を待って止まっているなら、
   そちらを先に動かす方が全体は速い（巡回のスコアで自動的に前へ出す）。

閉じる時は**何をして直ったか**を必ず書かせる。書かないと同じ相談が何度も来る。

### 「承認された」を完了にしない（実話）

**ある依頼で、人間が「OK、やって」と承認を出した。にもかかわらず複数セッションを経ても実行されず、
最後は本人が「もう10回以上言ってる」と不満を表明する事態になった。**

原因は、代行実行を試みた側が**対象が存在しない別の環境にログインした状態**で作業しており、
**誰もそれに気づかないまま「やっておきます」だけが繰り返された**こと。

**本質：「承認は得た」と「実際に完了した」の間の検証が抜けていた。**
承認をもらった時点で、頭の中では完了になっていた。

#### 状態を3つに割る（2つではなく）

```
承認待ち  →  承認済み・実行中  →  完了（効果を実測できた）
```

**真ん中を作らないと、承認＝完了に見えてしまう。**
`done` と呼べるのは**3つ目だけ**。承認は着手の許可であって、完了の証拠ではない。

Judgeの証拠（`evidence`）は、**承認の有無ではなく効果を測るもの**にする。
「人が承認した」は証拠にならない。「対象の環境で、望んだ変化が観測できた」だけが証拠。

#### 同じ依頼の繰り返しは「サボり」ではなく「経路の故障」

**同じ話題が3回以上出たら、その時点で最優先へ引き上げ、原因究明を先にやる。**
繰り返されているということは、**どこかが構造的に詰まっている**。
急かしても直らないし、担当を替えても直らない。

人間が「また言ってる」と気づくより先に、**機械が数えて気づく**ようにする
（ログの「判断待ち」「問題」を話題ごとに数えるだけでよい）。

#### 代行操作の前に「今どこに居るか」を読み上げる

**画面が出ている＝正しい場所に居る、ではない。**
組織名・プロジェクト名・アカウント名を先に読み取って報告してから操作を始める。
今回の事故は、これ1つで防げた。

### セーフティネット（省略不可）

- 最大反復回数の上限
- トークン／コスト／時間の上限
- **人間へ上げる時は具体的に**。「できませんでした」だけは禁止

### 効いているか確かめる（作っただけでは効いていない）

わざと壊して、ちゃんと落ちるか見る。落ちないなら、その見張りは飾り。

1. **解決不能タスク** … 諦めて正しくエスカレーションできるか（例：権限的に踏めない操作を「やった」と言わないか）
2. **確信に満ちた誤情報** … 一見完璧で1箇所だけ致命的に間違ったものをJudgeが見抜けるか
3. **同一モデル盲点** … Builder＝Judgeが同じモデルの時、自分の弱点に気づけるか
4. **コスト暴走** … 最悪ケースでもコスト < 価値か

**②が一番大事で、一番効いた。** 実例：開発環境で検索を試して「全部0件」に見え、
「この機能は行き止まりだ」と結論しかけた。実際は開発環境の索引が読み終わっていなかっただけで、
本番では十分ヒットしていた。**自信満々で、しかし完全に間違っていた。**
Judgeの正解データを「開発環境」ではなく「本番」にしてあったので、この主張はFAILで止まった。

→ **教訓：Judgeの正解データを、Builderが見ていた場所と同じにしない。** ここを同じにすると、
分離した意味がまるごと消える。

## 絶対ルール：確かめていないことを書かない

現在地メモは、**次のセッションが事実として信じて動く場所**。
ここに間違った既成事実を置くと、誰も疑わないまま伝播して事故になる。

- 分からない項目は空欄にせず **「未確認・要更新」** と正直に書く。
- 推測を書くなら「推測：〜（未確認）」と明示する。
  **推測すること自体は禁止しない。推測を確認済みと偽ることを禁止する。**
- 「実装済み」「反映済み」「直った」は、コミットID・実URL・検品の実行結果のどれかで
  裏を取ってから書く。取れないなら「対応済み・確認待ち」と、**対応と未確認を分けて**書く。
- 数字（件数・秒数・種類数）は、**測った日付と測り方**を添える。
  他所から借りた数字を自分の実測として書かない。
- 空欄を埋めるために想像で書かない。空欄のほうが、間違った記述よりはるかに安全。
- **言い換えで弱めない。** 失敗・未完了・エラーを「調整中」「課題が残った」のような
  やわらかい言葉にぼかさない。短く書いてよいが、事実の強さは弱めない。

## 設計上の落とし穴（先に踏んだもの）

- **セッションIDや常駐プロセスに状態を持たせない。**
  「あのセッションに聞けば分かる」は、そのセッションが消えた瞬間に全部失われる。
  状態はファイルに置き、コマンドで引く。実際に、常駐の巡回役が壊れて対象ごと成果を失った事故がある。
- **入口は1つにする。** 「あれとこれとそれを読んでから始めて」は必ず守られない。
  1コマンド／1ファイルに集約し、そこから先を辿れる形にする。
- **呼び名のゆれを吸収する。** 人間は毎回同じ語で呼ばない（特に音声入力）。
  台帳に別名を複数持たせ、表記ゆれで引けるようにする。当たらない語が出たら、その場で別名を1つ足す。
- **担当を細かく割りすぎない。** 割るほど「どれに当たるか分からない」が増える。
  迷ったら一番近い担当のメモを読ませる方が、読まずに始めるより常に良い。
- **現在地メモを長くしない。** 経緯を全部書くと誰も読まなくなり、更新もされなくなる。
  「今の方針・直近の決定・次にやること」の3点で足りる。経緯は判断ログ側へ。
- **台帳の参照先が消える。** ファイルを移動・改名した時、台帳は自動では直らない。
  ③の見張りで「参照先が実在するか」を必ず見る。
- **文章のルールだけでは同じ事故を繰り返す。** 「〜しないでください」と書くだけで終わると、
  数回後に同じ指摘をもう一度させることになる。できる範囲で exit code を返す機械の関所に変換し、
  無理なものだけ文章のまま残す（どちらか判定できる状態にしておく）。

## 実装例1（ジョイ・リリーフ・ステーション／卵商店街）

この型を実際に動かしている一例。**同じ形にする必要はない。**
リポジトリなら npm script、そうでなければ小さなシェル関数でも、
定型プロンプト1本でも、置き場所が決まっていれば成立する。

| 部品 | 実装 |
|---|---|
| ① 担当台帳 | `.claude/playbooks/roles.json`（12担当。別名・使命・読むもの・触る／触らない・落とし穴・検品・完成条件） |
| ② 現在地メモ | `.claude/playbooks/<担当名>.md` |
| ③ 見張り | `npm run role:check`（欠落・21日以上の古さ・一覧との不一致・参照先の消失・別名衝突・雛形のまま放置を検出。起動確認から毎回呼ばれる） |
| 読む | `npm run role -- <言われた言葉そのまま>` → 台帳＋現在地＋進行中作業との衝突＋既知の不具合を1枚に合成して出す |
| 書き戻す | `npm run role:handoff -- <担当名>`（雛形は空欄でなく「未確認・要更新」で埋まっている） |
| 完了の最終判定 | 鬼監督（親方）AI品質ゲート（`docs/ai/AI_QUALITY_GATE.md`）＋外部検品（独立セッションがURLを実測） |

## 実装例2（たまご進捗工場／tamago-shinchoku）— このSKILL自身が住んでいる現場

**②③がコードそのものとして動いている、より機械化が進んだ実装。** 担当が「人（セッション）」
ではなく「案件（号番号）」単位になっている点が実装例1との違いだが、3部品の対応関係は変わらない。

| 部品 | 実装 |
|---|---|
| ① 担当台帳 | `status/failures.md`／`status/failures.jsonl`（号ごとの落とし穴の蓄積）、各号の「作業ログ：成功例・失敗例」 |
| ② 現在地メモ | `status/genzaichi.md`（号・状態・担当の今の一枚）、`status/queue.json`（号ごとの題名・完了条件・経過） |
| ③ 見張り | `tools/kenpin_gate.py`（外部AIによる検品ゲート、自己申告を提出させない）／`tools/sekisho.py`（確認ページとpx・数字主張の実測一致）／`tools/oni_modoshi.py`（本番URLを実際に叩いてHTTP 200・本文400字以上・禁止語チェック。**自己申告の完了を機械的に受け付けない門**）／`tools/hikitsugi_gate.py`（引き継ぎを読んだことを機械で確認） |
| 読む | 新しいセッションは起動時に `status/genzaichi.md` と `ai-brain/kettei.json` を読み、`tools/hikitsugi_gate.py --generate`→`--answer-file`で読んだ証拠を残す |
| 書き戻す | `python3 tools/failures_ledger.py --quick "..."`（指摘をその場で1行）、`status/queue.json`は個別スクリプトから直接書かず`kenpin_gate.py`等のゲート経由でのみ更新（直接書き換えで台帳が消えた事故が複数回あったため） |
| 完了の最終判定 | `tools/oni_modoshi.py`（exit code による門。PASSしない限り案件は「完了」を名乗れず、自動的に再発車される） |

**この2例の違いが示すこと：** ①②③という骨格は変えずに、①台帳を「人の役割表」から「号ごとの失敗ログ」へ、
②現在地メモを「担当別プレイブック」から「号ごとの一枚サマリ」へ、③見張りを「起動時チェック」から
「常時の検品ゲート・門」へ、それぞれ対象ドメインに合わせて置き換えても型そのものは壊れない。
**これが「汎用スキルである」ことの実証。** 新しい3番目のプロジェクトに持ち込む時も、
①②③を自分のドメインの言葉に翻訳するだけで済む。

## 外部で独立に裏付けられた実例

深津貴之氏（note「OpenClawを活用した全自動開発のメモ」`note.com/fladdict/n/n5f315e408879`、2026-02-17・無料公開）が紹介する
**OpenClaw×Claude Codeの「プランナー・エグゼキューター」自律ループ**は、この型の3部品と驚くほど一致していた。

| OpenClaw×Claude Codeパターン | この型での対応 |
|---|---|
| `TODO.md`（未来の計画・実装側が管理、監督側は読取専用） | ②現在地メモ |
| `REPORT.md`（過去の事実・監査証跡） | ①台帳への実績追記・進捗ログ |
| Cron（5〜15分・異常時の自己修復＝フリーズ検知して再起動） | ③見張り（launchd・心臓・定期巡回） |
| Hooksによる即時継続トリガー（平常時、タスク完了の瞬間に次命令を発行） | ①②③の外側に置く拡張候補。安全性検証を経てから導入する |

牛尾剛氏（マイクロソフト／Azure Functionsチーム、著書『世界一流エンジニアの思考法』）の実践
（「計画とチェックリストを作り1つずつ更新しながら進める」「詰まったら数回試行→人間→別モデル」）、
およびDevin（Cognition社）公式ドキュメントが示す「エージェントに丸投げしてよい依頼の4条件」
（①完了条件が機械で検証できる②お手本がある③触る範囲が1つに閉じている④見積が小さい）も、
同じ骨格への別角度からの裏付けとして記録されている（詳細は実装例1側のリポジトリ内の調査記録を参照）。

## 導入手順（新しいプロジェクトへ持ち込む時）

1. **担当（または案件）を3〜7個だけ挙げる。** 最初から網羅しない。実際に繰り返し発生している作業だけ。
2. 各担当に**現在地メモを1枚**作る。中身は分からなければ全部「未確認・要更新」でよい。
   **想像で埋めない。**
3. 恒久情報（触ってはいけない場所・過去の事故・検品の仕方）を台帳へ移す。
   まだ無いなら空でよい。**事故が起きるたびに1行ずつ増やす**のが正しい育て方。
4. 「着手前に読む・終わる前に書き戻す」を、そのプロジェクトの入口ドキュメントへ**必須手順として**書く。
5. ③の見張りを用意し、起動確認かCIから毎回走らせる。**完了の最終判定だけは、できれば
   自己申告を受け付けない機械の門（URL実測・exit code）にする。**
6. 呼び名で引けない事故が起きたら、その場で別名を足す。
