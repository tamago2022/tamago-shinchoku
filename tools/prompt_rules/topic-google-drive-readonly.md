# Googleドライブは保管庫。読むと容量を食う（案件#642・2026-09-08）

たまごさんの言葉（そのまま）：
> 「俺はもう保管庫だと認識してるんだけれども。必要な時だけ引っ張ってくる場所。」
> 「ハードディスクにある素材なら、わざわざローカルにコピーする必要は無いわけでしょ。ドライブとなると、それをやんなきゃいけないってこと。そこを俺は把握してなかった。」

**Googleドライブは「読んだ瞬間にMacのディスクへ実体のコピーが落ちてきて、そのまま残る」場所。外付けHDDと違い、「読む＝容量を食う」。**

## 素材を探す順番（工場の全スクリプト・全指示文で共通）
**① Mac本体 → ② iMac HDD（外付け）→ ③ Googleドライブ。Driveは最後、そこにしか無い時だけ。**

## 守ること
- **Driveを丸ごと走査しない。** `du`・`find`・全件同期のような、Drive配下の全ファイルに触れる処理を新しく書かない。
  実例（642番で発見・修正済み）：`tools/disk_guardian.py`が15分おき（1日96回）に`du -sm`でGoogle Driveの「マイドライブ」直下フォルダを舐めていた。実測で1回5.6秒かかっており、1日あたり約9分間Driveに触り続けていたことになる。1日1回だけ実測してキャッシュを返す方式に直した（`GDRIVE_CHECK_INTERVAL_SEC`・`gdrive_big_folder_warnings()`）。
- **たまごさんが「Driveに置いた」と言ったものだけ、その1つのファイルを取りに行く。** フォルダ・ライブラリごと丸ごと落とさない。
- **Driveから読んだら、読み終わったら手元から捨てる**（`fileproviderctl evict`等）。エラーになる場合はその事実を記録し、削除できない前提で次の手を考える（640/641番の実測：`contentPolicy pin`により機械的なevictは拒否される既知の壁がある。同じ経路を3回目試さない）。
- Eagleライブラリなど、iMac HDDに実体があるものは、Driveを経由せず**HDDから直接読む**。`tools/eagle_drive_sync.py`は読み込み元がiMac HDD、Drive側へは書き込みのみで走査はしていない（既に原則どおり）。新しく同期・バックアップの仕組みを作る時も、この向き（HDD→Driveへ書く、Driveから読み戻さない）を崩さない。
- Driveのローカル使用量は`tools/disk_guardian.py`の日次キャッシュ（`status/gdrive_daily_usage.json`）で追える。増えていたら、その日実行されたタスク（`status/history.jsonl`等）と突き合わせて原因を特定する。
