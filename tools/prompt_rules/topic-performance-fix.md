## ★★★「重い」を直すときの手順（2026-09-08・usutaku さんの型を採用）

出典：usutaku（@usutaku_channel）2026-09-07 のポスト。たまごさんが持ち込んだ。
**「重いからサクサクにして」だけでは直らない。**この順番でやる。

### 手順（この順番を飛ばさない）
1. **遅さを再現する**（まず自分で遅いのを見る。見ずに直さない）
2. **今の処理時間を測る**（秒で。体感で書かない）
3. **どの処理に時間がかかっているか調べる**（当てずっぽうで直さない）
4. **原因を、初心者にも分かる言葉で説明する**（専門用語で書かない）
5. **効果が大きく、変更リスクが小さいものから直す**
6. **変更前と変更後を、同じ条件で測る**
7. **既存の機能が壊れていないかテストする**

### 禁止
- **推測だけで「速くなりました」と言わない。必ず測定結果を出す。**
- **いきなり大規模に書き直さない。**
- **一度に複数の大きな変更をしない。**原因と効果を追跡できる単位で変える。

### 実例（この型が効いた例）
> 「ローディングに2.2秒かかる場面で、**フォントの読み込みに1.4秒**かかっているから、それを改善する」
> → 書体を待たずに画面を出す形に変えただけで、**1.72秒 → 0.33秒（約81%短縮）。**
> 作り手からすると「特にフォントにこだわりがないなら速さを優先しよう」となる。
**どこが遅いかが分かると、判断ができるようになる。**それがこの手順の本当の価値。

### 依頼するとき／自分に問うとき、必ず埋める5行
```
遅い操作：
今の待ち時間：約◯秒
目標：◯秒以内
発生条件：
変えてはいけないもの：
```
★**「目標値」と「変えてはいけないもの」の2行があるかどうかで、返ってくるものがまるで違う。**
 （リプ欄より。「今が不便」は言えても「こうなってほしい」が言えないと直らない）

### ただし、絞りすぎない
リプ欄に大事な反論があった：
> 「**特定したり限定した指示にすると、その周辺しか原因を探らなくなる。**」（フレーム問題・アンカリング）
★**目標と制約は決める。でも「原因はここだ」と決めつけない。**
 手順3（どこが遅いか調べる）は、**先入観なしに全体を測ってから絞る。**
