## ★★★ 便を出す前に、門の紙を1枚だけ読む（2026-09-24・実測から）

### 読む紙は1枚

```
status/public/hassha_gate.json
  hasshaOK     … false の間は本物の便を1本も出さない
  maxParallel  … この本数を超えて出さない
  why          … 駄目な理由（そのまま人に見せられる1行）
```

書いているのは `tools/inochi.py`（心臓から30秒おき）。★古い紙は存在しない。

### 守る数字は1つ

> **同時に走らせるのは 2本まで。**（紙の `maxParallel` がそれより小さければ、小さい方）

### なぜ（★推測ではない）

`status/ochita.jsonl` 18件の実測：
同時**2本で33%・3本で50%・4本で80%・6本で100%**の回で便が落ちている。
落ちた回の容疑は**12回すべて「ログイン切れ」**（枠の不足は0回）。

`auto_launch.log` × `machine_health.jsonl` の実測（スワップ中央値）：
1本 11.0GB → 2本 12.3GB → **3本 16.4GB → 4本 18.3GB**。空きメモリは6〜8GBしか無い。
＝**3本目から機械が溺れる。**

2026-09-24 に4本走ったのは、本数の数字が3か所にあって緩い方が採られたため
（`machine.json` の safeMax=4 ／ 機械自身の実測 cap=1 ／ `launch_cap.json` が4日古い cap=5）。
**だから門を1枚にした。数字を増やすときも、この紙の出どころ（`moto`）を書き替えずに増やさない。**

### 鍵が死んでいる間にやること

`hasshaOK: false` の理由がログイン切れなら、**便を出さずに待つ**（出しても起動した瞬間に落ちる）。
たまごさんへの頼み方は1行だけ：
> いつものClaudeのアプリで1回ログインし直してください。

戻ったことは `auth_keeper.py` が自分で気づいて門を開ける。人が門を開けに行かない。
