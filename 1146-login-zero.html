2. 手は最低5つ並べた。そのうえで選んだ

① 公式の長期トークン／APIキーに置き換える採用・本命

サービス自身が「機械用の鍵」を用意している場合、これが一番強い。ブラウザを一切使わないので規約にも触れない。Buffer・GitHub・Supabase・Claude はここに入る。

② OAuth の refresh_token を回し続ける採用・次善

access_token が切れても refresh_token で自動で作り直す。Lovable・Spotify はこれ。落とし穴：refresh_token は1回使い切りのサービスが多い（Buffer・Xとも公式に明記）。古い方をもう一度送るとそのアプリの鍵が全部失効して、人が再許可するはめになる。必ず最新の1本だけを保存して古いのを捨てる。

③ ブラウザのログイン状態を保存する（Playwright の storageState／永続プロファイル）採らない

Cookie と localStorage をファイルに落として使い回す手。やめた理由が世界中に転がっている：多くのサイトはセッションを24時間前後で切る／月曜に取った状態が金曜には死んでいる／Cookieを強く切るサイトと毎回回る2段階認証があると破綻する／サイトごとにログイン処理を書くのが保守地獄になった。さらに LinkedIn は利用規約でヘッドレスブラウザを名指しで禁止、Instagram も公式API以外の自動化を禁止。ブラウザでログインする自動化は、プラットフォームから見ると bot と区別がつかない。だから採らない。

④ パスワードマネージャCLIで人が打たずに通す採らない

1Password の service account（OP_SERVICE_ACCOUNT_TOKEN を置くと op run が対話なしで通る）や Bitwarden の personal API key。仕組みとしては正しい。ただしこれは「鍵を安全に取り出す」道具であって、取り出した先でブラウザにパスワードを打ち込むなら③の問題がそのまま残る。加えて Bitwarden は API key でログインしたあと結局 bw unlock にマスターパスワードが要る（--passwordenv で環境変数に置く形）。こちらがパスワードを直接扱う形になるので採らない。①②が効かないサービスが出てきたら、その時だけ再検討する。

⑤ 2段階認証（TOTP）を自前で計算して通す採らない

otpauth などのライブラリに同じ秘密鍵を渡せば、認証アプリと同じ6桁が作れる。技術的には動く（Checkly が手順を公開している）。採らない理由：③とセットでしか意味がなく、③が規約に触れる。そして2段階認証を機械に持たせた時点で、2段階認証をかけた意味が消える。

⑥ デバイスコードフロー（画面の無い機械で1回だけ人が承認する）部分採用

機械が短いコードを表示して、人は手元のスマホで1回だけ許可する。claude setup-token と gh auth login が実質これ。「そこだけ人」を最小の1回に圧縮する形として、①が無いサービスで使う。

3. 一番効く1つ：Buffer をキー1本にする

89回のうち64回（Buffer 52＋X 12）がこの1手で消える。しかも0円。Buffer は2026年5月に公開API・MCP・CLI を出して、無料プランでも使える。

  1. ここだけ人の手が要る（1回だけ）： publish.buffer.com/settings/api を開いて「Create a new API key」。出てきた鍵を ~/.tamago/keys/api_keys.env に BUFFER_API_KEY=… で貼る。
    こちらはパスワードを扱わない。鍵の値もこのページには一切書かない。
  2. そのあとは機械だけで回る。動かす口はもう作って置いてある： 
    python3 tools/1146_buffer.py channels
python3 tools/1146_buffer.py post --channel <id> --text "本文" --at 2026-09-27T09:00:00+09:00
python3 tools/1146_buffer.py post --channel <id> --text "本文" --dry-run   # 1バイトも送らず中身だけ出す
  3. Claude から直接使うなら MCP を足すだけ（同じ鍵）： 
    { "mcpServers": { "buffer": {
    "type": "http",
    "url": "https://mcp.buffer.com/mcp",
    "headers": { "Authorization": "Bearer ${BUFFER_API_KEY}" }
} } }
  4. X は Buffer のチャンネルとして繋ぐ。Xに直接ログインする用事が消える。

動かした証拠：--dry-run が送信内容（createPost ミューテーション・channelId・dueAt）を正しく組み立てて出すところまで確認済み。鍵が無い時は「どこで作るか」を書いて止まる。実際の送信は鍵を貼った後。

4. 切れたら自動で気づく（鍵の見張り）

SREの世界の定石は「切れてから慌てない。期限の手前で鳴らす」。トークンの寿命の75〜80%を過ぎたら先に更新する、401が返ったら再取得に落ちる、という二段構え。ただしrefresh_token 自体が死んだ場合は機械では戻せないので、そこは人を呼ぶしかない。だから「呼ぶ回数を数えられる形」にした。

python3 tools/1146_kagi_mihari.py            # 人が読む形
python3 tools/1146_kagi_mihari.py --json     # 機械が読む形（status/1146/kagi_jotai.json に出る）
# 終了コード 0=全部生きている / 1=期限が近い / 2=死んでいる鍵がある

鍵の値は1バイトも読まない。「置き場に在るか」と「あと何日か」だけ。取得日が台帳に無いものは推測で埋めず「残り日数が出せない」と黄色で出す。
テストで動作確認済み：期限365日・取得2026-01-01の鍵を「あと97日／青」、中身が空の項目を「赤」、ファイルが無いものを「赤」と正しく判定した。
台帳は status/1146/kagi_daicho.json。毎日1回回せば、上の表の「今 年◯回」が置きではなく実測になる。

5. 採らなかった手と、その理由

採らなかった手理由
X API を直接叩く0円で出来ない。2026-02-06 に新規向けの無料枠が廃止され従量課金へ。投稿1件 $0.015、リンク付き $0.20、読み取り1件 $0.005 という報告。※この価格は個人ブログ複数の一致で、公式ページでは未確認＝弱い情報。→ Buffer経由にすれば0円で済むので、確認を待たずに回避できる。
Lovable の公式APIキー課金。公式FAQに「APIキーの作成には Business または Enterprise プランと、ワークスペースのowner/admin権限が要る」と明記。
ブラウザにログインを保持させる
（storageState／永続プロファイル）		規約と、壊れやすさ。LinkedIn はヘッドレスブラウザを名指しで禁止、Instagram は公式API以外の自動化を禁止。技術的にも24時間〜数日で切れる実例が多数。
パスワードマネージャに打たせるこちらがパスワードを直接扱う形になる。Bitwarden CLI は API key でログインしても bw unlock にマスターパスワードが要る。原則に反するので採らない。

Buffer を OAuth で繋ぐ動くが、refresh が1回使い切りで、間違えると全部の鍵が失効して人が再許可する。APIキー1本の方が手が減る。目的は手を減らすことなので採らない。

6. 「永久」を信じた仕組みが死んだ実例

  • Spotify（2026年）：長らく refresh_token は無期限だった。2026-06-18に「6か月で失効させる」と告知、既存アプリも2026-07-20から対象。期限は最初に許可した日から数え、更新しても伸びない。世界中の「一度作れば一生動く」仕組みが一斉に止まり、MagicMirror のモジュールは再認証フローを足したフォークが出た。教訓：寿命は変更される。だから見張りが要る。
  • X（OAuth 2.0）：offline.access を付けているのに refresh_token が切れるという報告が開発者フォーラムに何年も積み上がっている。access_token は2時間、refresh_token は6か月・1回使い切り。
  • ブラウザ自動化：storageState を使っていた人が「Cookieを強く切るサイトと、毎回回る2FAで破綻した。サイトごとにログイン処理を書くのが保守地獄になった」と書いて乗り換えている。※出典が個人ブログ＝弱い情報。ただし同じ趣旨の記述が複数ある。
