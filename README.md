# 進捗表（スマホ用アプリ）

> ## ★★ 報告の形は `status/HOUKOKU_NO_KATACHI.md` が最新（2026-09-24）★★
> **1行＋URL。以上。**原因・経緯・試したこと・手順・謝罪・数え方・ファイル名・行番号は書かない。
> URLが無い報告は出さない。まだ治っていないものは報告しない。
> このREADMEの他の場所にある古い報告フォーマットより、そちらが優先。

たまごさんがスマホのホーム画面から開くタスク進捗表。ごきげん補給所とは別の独立したアプリ。

- 土台：Obsidian Vault の `AI出力/_ルール/進捗表.html`（2026-09-02 に移植）

## 発車待ちの軽量表示（2026-09-10・726番）

`status/queue.json`（発車待ち台帳の正本）はwhat/result本文込みで1.5MB超あり、進捗表が毎回これを
まるごと読むと重い。そこで表示用に`status/queue_light.json`（`tools/build_queue_light.py`が生成、
n/title/status/priority/model/updatedAt等だけ・80KB台）を作り、進捗表はまずこちらだけを読む。
`<details>`（くわしく）を開いた瞬間だけ、その1件のwhat/resultをフルの`queue.json`から遅延取得する
（`fetchQueueFull()`）。done/cancelledは直近分だけしか`queue_light.json`に含めない。

## PWAとブラウザで中身がズレる件（2026-09-11・726番）

`data.js`/`queue_light.json`等はすべて同一オリジンの相対パスで読むので、コード自体は
PWA・ブラウザどちらでも同じ場所を見る。ズレの実体は「PWAとブラウザがそもそも違うURL
（違うオリジン）を開いている」ことがほぼ全て（PWAは古いURLでホーム画面登録されたまま等）。
JS側から強制的に合わせることはできないため、正規URL（`https://tamago2022.github.io/tamago-shinchoku/`）
と違う場所を開いている時は画面上部に警告バナーを出す（`checkCanonicalLocation()`、家のWi-Fi内で
Macから直接開く`isLocalRelay`系は意図した別経路なので対象外）。
また、通信が細い回線で`fetch`や`<script src>`の応答が返らないまま止まる箇所（`checkVersion`／
`priority.json`取得／`data.js`等の読み込み）に明示的なタイムアウトを追加し、詰まっても
「読み込みに時間がかかっています」が無言のまま何十分も出続けないようにした（一定回数を
超えたら失敗と表示し、手動で読み直すリンクを出す）。

## Dispatchへの完了報告（2026-09-06新設・413番）

子セッションが完了するたびに `tools/auto_launcher.py` の `harvest()` が
`status/dispatch_outbox.jsonl` へ1行追記する（JSON Lines。1行＝1件の完了）。
項目：`ts`（完了時刻）／`n`（番号）／`title`（題名）／`ok`（成否）／
`elapsedMin`（着火〜完了の経過分）／`urls`（本番・確認ページURL）／`result`（報告文の抜粋）。

**Dispatch（たまごさんとの会話）は、会話開始時に次の2ファイルを読み比べて報告する：**

1. `status/dispatch_outbox.jsonl` の全行
2. `status/dispatch_reported.json` の `ns`（すでに報告済みの番号一覧）

`ns` に無い `n` の行だけを「まだ報告していない完了」として、3時間の区切り（`elapsedMin`）が
分かる形でまとめて話す。話し終えたら、報告した `n` を `dispatch_reported.json` の `ns` へ追記する
（読み取り・突き合わせ側は今回新設せず、既存の `ns` 台帳とこの運用手順だけで足りる）。

## 「◯◯直ってないよ、やり直して」の一言で列へ戻す（2026-09-09新設・680番）

たまごさんが会話で「直ってない、やり直して」と言った時、Dispatch（たまごさんと会話しているセッション）が
番号を聞き返さずその場で使う道具：

```
python3 tools/owner_redo.py --text "<会話に出た手がかり・題名の一部>" --note "<何が直っていなかったか・空でもよい>"
```

- `--n <番号>` が分かっていればそちらを優先して使う（一番確実）。
- `--text` だけの時は `status/queue.json`（＋完了済み控えの`deleted.json`）の全項目の題名・依頼文と突き合わせ、
  1件に絞れたときだけ実行する。**絞れない時は候補一覧を出すだけで、当てずっぽうでは戻さない**
  （最後の行が `OK #n ...` なら成功、`AMBIGUOUS ...`／`NOTFOUND ...` なら見送り）。
- 実体は進捗表の「↩︎やり直し」ボタンと同じ`tools/command_ingest.py`の`queue_redo()`。新しい別処理は作っていない。
- 戻すたびに「何が直っていなかったか」（`--note`）を1行、`what`の末尾へ`【たまごさんのやり直し指摘・N回目・日時】`の形で追記する。
  次にこの番号へ着火するセッションが同じ間違いを繰り返さないための申し送り。
- `ownerRedoCount`（この経路でのやり直し回数）が**3に達したら**、優先度を最優先へ上げるだけでなく、
  「同じ直し方を繰り返さず原因の調べ方・実装方法を変えること」を`what`へ明記し、
  `status/dispatch_outbox.jsonl`（`type: "owner_redo_escalation"`・`n`は`"<番号>-redo3"`で通常の完了報告と衝突させない）と
  `status/failures.md`へ自動で1件ずつ記録する。同じ経路で4回目を漫然と繰り返さないための仕掛け。
- 進捗表（スマホ）側の「↩︎やり直し」ボタンも同じ`note`欄を使う。押すと「何が直っていなかったか」を聞くプロンプトが出て、
  空でなければ`sendCommandWithExtra()`経由で`note`付きの`queue_redo`が送られる（`queue_add`の`priority`と同じ「commandオブジェクトに追加キーを乗せる」やり方）。

## 案の比較台（2026-09-11新設・747番）

たまごさんの言葉（そのまま）：「今スマホで見てるから、出力フォルダじゃなくて…GitHubか、どれがいいかタイムラインで

- 場所：`share/compare/`（一覧は`share/compare/index.html`、`share/index.html`からもリンク）。
- 作り方：`tools/make_compare_page.py --n <番号> --slug <英語名> --title "..." --what "..." --item "表示名|GIF相対パス|フレームdir|フレーム枚数"`
  （`--item`を2つ以上渡せばA案・B案が横並びで両方ループ再生される。狭い画面では自動で縦積みに変わる）。
- コマ送り：`--item`の3・4項目目にフレーム画像（PNG/JPG連番、`fN.拡張子`という名前）のディレクトリと枚数を渡すと、

- 「これにする」ボタン：新しい中継所は作らず、進捗表(index.html)の優先度・リモコンと**全く同じ道**
  （`status/relay.json`の中継所URLへ`{"action":"queue_add",...}`をPOST）に乗せた。中継所が死んでいる時は
  `localStorage`の`shinchoku_pending_cmds`（進捗表と共有）に貯め、次に進捗表を開いた時にまとめて送られる。
- 1MB超ガード対策：GIFはそのままだと簡単に1MBを超える（実例：747番のB案は元1,027,176バイトで超過）。
  Pillowで`quantize(colors=100, dither=Image.Dither.NONE)`すると、ノイズをほぼ出さずに半分程度まで縮む
  （dither有り／256色のままだと元とほぼ同サイズで縮まなかった実測値）。`make_compare_page.py`は生成前に
  置いた画像のサイズを見て、1MBを超えていれば警告を出す（自動では縮めない。縮め方は毎回内容を見て決める）。

### ② 掃除機：`tools/chrome_tab_sweeper.py`（最後の保険）

セッションが落ちた・忘れた時のために、**セッションの外側（Mac上のこの工場）から**掃く。

```
python3 tools/chrome_tab_sweeper.py --recon              # 数えて記録するだけ（1枚も閉じない）
python3 tools/chrome_tab_sweeper.py --sweep --force      # 今すぐ掃く
python3 tools/chrome_tab_sweeper.py --sweep --dry-run    # 判定だけ
```

**安全側に倒す設計（ここを緩めない）：**

- **Chromeが起動していなければ何もしない。**生死判定は `pgrep` のみ。
  `osascript -e 'tell application "Google Chrome" …'` は**Chromeが起動していないと起動してしまう**ため、
  生死判定には一切使わない（憲法「たまごさんの画面を奪わない」）。
- **`activate` しない。**前面に出さない。裏で処理する。
- **ウィンドウの前面タブ（active tab）は閉じない。**たまごさんが今見ている可能性があるため。
- **ウィンドウの最後の1枚は閉じない。**ウィンドウごと消えるため。
- 閉じる直前に**URLを照合してから閉じる**（`SKIP_MOVED`）。タブが動いていたら取り違えずに見送る。
- **後ろのタブから閉じる。**前から閉じるとindexがずれて別のタブを閉じる。
- 閉じてよいのは次の3つだけ。それ以外は**全部残す**（見分けがつかないものは残す＝誤って閉じる方が害が大きい）。
  1. `CLOSE_EXACT` … 空タブ（`about:blank`・新しいタブ）。閉じても何も失われない。
  2. `CLOSE_PREFIXES` … Claudeが検品で開く `share/check/` のページ。
  3. **★一度も前面に来たことがないタブ**（後述）。
- さらに `NEVER_CLOSE_PATTERNS`（X・YouTube・Lovable・ChatGPT・Gmail・GitHub・Devin・LINE・
  claude.ai・`file://`・拡張機能・`chrome://` 設定系）に1つでも当たったら、

URLの見た目では、Claudeが開いたのか たまごさんが開いたのか分からないタブが必ず残る。
そこで**観測**を証拠にする。この掃除機は心臓から15秒おきに `--recon` で呼ばれ続けるので、
各タブが「これまで一度でも前面（active）になったか」を `status/chrome_tab_history.json` に積める。

- たまごさんが自分で開いたタブは、**開いた瞬間に必ず前面になる**（＝`everActive`が立つ）。
- 機械が裏で作ったタブは、何時間経っても一度も前面に来ない。
- → **2時間以上・120回以上観測して一度も前面に来ていない**なら孤児と見なす（`looks_orphan()`）。
- **観測が10分以上途切れたらその記録は捨てて数え直す。** Chromeを終了→再起動すると前回のタブが
  復元されるが、復元直後は たまごさんのタブでも「まだ一度も前面に来ていない」状態になる。
  古い記録を引き継ぐと**たまごさんのタブを孤児と誤判定して閉じてしまう。**

**★たまごさんの開いているタブのURLは、絶対にgit管理下へ書かない。**
このリポジトリは GitHub Pages で公開されている。記録は `status/chrome_tabs_recon.json`（URL入り）と
`status/chrome_sweep.json`（件数だけ）に置く。**どちらも `.gitignore` の `status/*` で除外済み**で、

### ③ 定期的に掃く（新しい常駐・定期タスクは増やさない）

### ④ おまけ：取り残された `.git` ロックで工場のgitが丸ごと止まる事故の自己修復

この931番の作業中に実際に踏んだ穴。**サンドボックス（Cowork）側のセッションが `git commit` の
途中でタイムアウト打ち切りされると `.git/index.lock`（実測424,056バイト）が取り残され、
以後このリポジトリの add/commit が全て `rc=128` で失敗する。**5分便も発車もgitを使う工程が全部止まる。
しかも**マウント越しには `unlink` が許されておらず（Operation not permitted）、
ロックを作った本人が自分で片付けられない。**

→ `tools/git_lock_reaper.py`（`worktree_reaper.py` と同じ立ち位置・心臓に相乗り）。
**両方を満たしたロックだけ消す。1つでも欠けたら触らない：**

1. ロックのmtimeが**300秒より古い**（＝今まさに書いている最中ではない）
2. **gitのプロセスが1本も走っていない**（`pgrep -x git`。判定できない時は「走っている」側に倒す）

消す対象は名指しした7種だけ（`index.lock` / `next-index-*.lock` / `HEAD.lock` /
`ORIG_HEAD.lock` / `config.lock` / `packed-refs.lock` / `refs/**/*.lock`）。
**ワイルドカードで `.git` 配下を舐めない。** 片付けたら既存の `status/git_rebase_incidents.log` へ1行残す。

**★heartbeat.sh に行を足しただけでは効かない（この作業で実測して分かったこと）：**
**走っている心臓（bash）はループ本体をメモリに持っているので、心臓が入れ替わるまで新しい行は実行されない。**
一方 python のファイルは呼び出しごとに読み直される。そこで `git_lock_reaper.reap()` を関数として公開し、
**毎サイクル必ず呼ばれる `tools/launch_watchdog.py`（894番・「止まった瞬間に自分で立て直す」係）から
呼ぶ**ようにした（`launch_watchdog.py` が `genzaichi.check_launch_silence()` を借りているのと同じ形）。
心臓の入れ替えを待たずに効く。**心臓・5分便への行も残してあるので、経路は3本ある。**

もうひとつの実測：この工場は `auto_launcher` / `command_ingest` / 5分便がgitを絶えず叩いているため、
「gitプロセスが1本も無い時だけ消す」だけでは**静かな瞬間が来ずロックが何十分も片付かない**
（`refs/heads/main.lock` が24分放置されたのを実測）。正常なgit操作が15分ロックを握ることは無いので、
**15分を超えたらgitが走っていても消す**（`HARD_STALE_SECONDS`）。これが無いとこの道具は
「動いているのに直らない」状態になる。

実機で通した記録（2026-09-18・すべてMac側の実行ログ）：
```

02:26    2件とも片付き、git が復活
02:31:44 🧹 .git/HEAD.lock（5分放置・gitプロセスなし）
02:37:39 🧹 .git/HEAD.lock（5分放置・gitプロセスなし）
02:57:34 🧹 .git/refs/heads/main.lock（24分放置・15分超なのでgit走行中でも片付けた）
```

git走行中6分→残す／git走行中20分→消す。

### ★★★ Cowork（サンドボックス）側から git commit / push をしない（2026-09-18・実測の結論）

この931番の作業で**同じ穴に4回落ちた**ので、原因と作法を残す。

**なぜダメか（実測）：**

- サンドボックスはマウント越しに `.git` 配下を**作れるが消せない**（`unlink`＝Operation not permitted）。

- 取り残されたロックは**工場全体のgitを止める**（add/commit/pull/pushが全て `rc=128`）。
  実測：`git pull(merge) が失敗` が 03:00:23 に発生。掃除機が拾うまで最大15分かかる。
- `git commit` は `.git/COMMIT_EDITMSG` を書いてから読み直すが、この読み直しが
  マウント越しでは `could not read commit message: No such file or directory` で落ちる（実測）。
  そのため `commit-tree` + `update-ref` の配管コマンドを使う必要があり、さらに
  **`update-ref` が `HEAD.lock` を残す。**
- `push` はできない（サンドボックスに `gh` が無く、`gh auth git-credential` が引けない）。

**ではどうするか：**

```
git add -- <触ったファイルだけをパス指定>     # ← ここまでで止める
```

**あとはMac側の5分便（`machine_status_push.sh`）が `git commit` → `pull` → `push` をやる。**
`git add` はロックを残しにくく（残っても掃除機が拾う）、5分便はMac上で動くので
`unlink` も認証も問題なく通る。**「積むだけ積んで、押すのはMacに任せる」**のが正しい分担。

**★`git add` は必ずパス指定で。**`git add -A` / `git add .` は絶対にやらない

過去にqueue.jsonが28件/5件/271件消えた3回の事故と同じ経路）。
