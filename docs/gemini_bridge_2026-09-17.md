## 1. 下敷き：Spotify社 Portal/shunt（2026-09-03公開）

- Claude CodeのPreToolUseフックで「大きいファイルの読み込み」（`Read`ツール、または
  `cat`/`head`での大きいファイル読み込み）を検知し、安いワーカーモデル（Gemini 2.5 Flash）へ
  中身の要約・調べ物を委譲する仕組み。
- **委譲してよいのは「読む・要約する」仕事だけ。** 編集・デバッグ・設計判断・安全性が絡む推論には
  使わない。Spotifyの実測でも、ワーカーモデルはスレッド安全性バグを見逃した（判断まで安いモデルへ
  渡すと事故る、という実例）。
- Javaモノレポでの実測：bulk-read（複数ファイルへの質問をまとめて委譲）で平均**90%のトークン削減**。
- 委譲1回あたり**10〜30秒のレイテンシ**が発生する。350行未満の小さい読み込みには向かない
  （委譲のオーバーヘッドが節約を上回る）。

### Anthropic公式：Prompt Caching（`claude.com/blog/prompt-caching`、2026-09-17に実際に開いて確認）

- 原文どおりの数字：**「reducing costs by up to 90% and latency by up to 85% for long
  prompts」**。
- 実測例（原文どおり）：本1冊分（10万トークン）をキャッシュして対話 → レイテンシ
  11.5秒→2.4秒（-79%）、コスト-90%。マルチターン会話（10ターン）→ レイテンシ約10秒→約2.5秒
  （-75%）、コスト-53%。
- 何に使う仕組みか：**長文ドキュメントとの対話・要約・コーディング支援・エージェントのツール
  利用**（＝今回のGemini委譲と同じ「調べ物・要約」寄りの場面で効果が出ている）。
- **今回の仕組み⑫との違い（向かない用途とは別に、混同しないよう明記）：** Prompt Cachingは
  「同じ内容を繰り返し読む」時にキャッシュが効く仕組みで、初回の読み込みコスト自体は下がらない。
  Gemini委譲（別モデルへ渡す）とは仕組みが違う節約手段であり、両方使うことも可能。
- 向かない用途：本文に明記なし（未確認）。

## 4. 今回tamago-shinchoku向けに作った3点

### 4-1. `tools/gemini_delegate.py`

Gemini API（`generativelanguage.googleapis.com`のREST APIを`urllib.request`で直接叩く。
外部ライブラリの追加インストールなし・python3標準ライブラリのみ）を使うCLI。

```bash
# 複数ファイルへの質問をまとめて委譲する
python3 tools/gemini_delegate.py bulk-read --question "質問文" --paths file1 file2 ...

# 1つの大きいファイル・ログを要約する
python3 tools/gemini_delegate.py summarize --path 大きいファイル --question "質問文（省略可）"
```

- システム指示に「正確なコード分析者として、簡潔に構造化された箇条書きだけで回答する。挨拶・
  前置き・説明文は禁止」を必ず含めている（この指示が無いとMarkdown装飾だらけの出力になり、
  かえって無駄になるとSpotify記事にある通り）。
- `GEMINI_MODEL`環境変数でモデルを変更可能（デフォルト`gemini-2.5-flash`）。
- 429/503は指数バックオフで2〜3回リトライ。
- 標準エラー出力に委譲にかかった時間（秒）とおおよその文字数を出す（委譲の効果が見えるように）。
- ファイルが存在しない・読めない場合は分かりやすいエラーで終了コード1（工場全体は止めない）。
- **`GEMINI_API_KEY`が`.env`に無い場合は、キーの値を一切扱わず、分かりやすい日本語メッセージを
  出して終了コード1で自分だけ終わる。**

### 4-3. `tools/estimate_gemini_savings.py`

「大きい読み込みがどれだけの頻度で発生していそうか」を実測ログから概算するスクリプト。

**当初案からの変更点（正直な記録）：** 依頼時は`status/auto-launch-*.log`（762件）をサンプルする
想定だったが、実際に開いて確認したところ、このログには①起動時の宣言行と②終了時のJSON要約
（`permission_denials`＝**却下された**Bash/Edit/Write/Task呼び出しのみ）しか記録されておらず、
**成功したReadツール呼び出しの記録が一切含まれていなかった**（Readは許可プロンプトが不要なため
却下履歴にも残らない）。そのため、同じセッション群の実体である
`~/.claude/projects/-Users-mac-Desktop-tamago-shinchoku/*.jsonl`（Claude Codeが各セッションの
全tool_use/tool_resultをそのまま保存している生トランスクリプト）を直接サンプルする方式に切り替えた。

```bash
python3 tools/estimate_gemini_savings.py
```

## 5. `tools/estimate_gemini_savings.py`の実行結果（2026-09-17実測・直近40セッション）

```
サンプルしたセッション数: 40（~/.claude/projects/-Users-mac-Desktop-tamago-shinchoku）
Readツール呼び出しの総数（結果を確認できたもの）: 88
うち350行以上の大きい読み込み: 4
大きい読み込みの割合: 4.5%
Read呼び出しが1回以上あったセッション数: 4 / 40
```

**この数字から分かること・限界：**

- サンプルした40セッション中、`Read`ツールを1回でも使ったセッションは4本のみだった。他の
  多くのセッションは、目視で確認したところ`Bash`経由の`sed -n 'X,Yp' ファイル`・`grep -n`・
  `cat | tail`のような**部分読み込み**で大きいファイルを避けている実態が見えた（work自体が
  すでに「全部読まない」工夫をしている）。
- それでも88回の`Read`呼び出し中4回（4.5%）は350行以上の大きい読み込みだった。頻度としては
  高くないが、ゼロではなく、委譲の余地は実在する。
- この計測は「Readツールの呼び出し」だけを対象にしており、Bashの`cat`/`sed`経由の大きい読み込み
  は数えていない（依頼文にある「catやheadでの大きいファイル読み込み」も本来は検知対象だが、
  Bashコマンドの中身からファイルサイズを正確に判定するのは今回のスクリプトの範囲外とした）。
  正確なトークン数の計測ではなく、あくまで「発生頻度」の概算である。

## 6. Google/YouTube/X連携の調査結果

- **YouTube**：`.env`に既に`YOUTUBE_DATA_API_KEY`がある。動画の字幕・概要欄テキストを取得して
  Geminiへ渡し、要約・トレンド調査させる設計は技術的に可能（技術的な接続経路が既に揃っている、
  という意味。今回は未実装）。Gemini API自体には動画本体を直接読ませるマルチモーダル機能も
  あるが、これも今回は未実装・将来検討。
- **X（Twitter）**：公式APIが有料化されており、Gemini経由であっても無料での大量データ取得は
  困難。この制約は裏取りできていない楽観的な見通しを書かず、正直にそのまま記録する。

## 8. 向かない用途セット（再掲・最重要）

- コードの編集・デバッグには使わない。
- 設計判断・アーキテクチャの意思決定には使わない。
- 安全性が絡む推論（削除してよいか・公開してよいか・スレッド安全か等）には使わない。
- 350行未満の小さい読み込みには使わない（委譲のオーバーヘッドが節約を上回る）。
- 判断は常にClaude側が持つ。Geminiが返すのは「調べた結果の要約」だけ。
