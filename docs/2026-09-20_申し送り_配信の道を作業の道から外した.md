# 963番 申し送り：配信の道を、作業の道から外した

2026-09-20 未明に切り替え済み。**たまごさんに渡したURLは1本も変わっていない。**

---

## 何が詰まりの元だったか（実測）

- gitが詰まった回数 **232回**（push失敗95／「向こうが先で合流できない」64／取り残しロック23／pull失敗9）
- `tools/machine_status_push.sh` が **5分おきに `status/public/` の写しを main へ commit+push** していた。実測 **1日73回**。
  main には人間の書き手9人と worktree 17個が居るので、機械が毎回その列に割り込んでいた。
- さらに `.github/workflows/pages.yml` が **main への push のたびにリポジトリ丸ごと(681MB)** を
  Pages へ上げ直していた。実測 **1日274回**。
- おまけに、下の `git pull` と `git push origin main` は**出すものが1つも無い回でも毎周（約60秒おき）無条件で**走っていた。

つまり「配信の道」と「作業の道」が同じ1本だったのが原因。穴が開くたびに段ボールを貼っていた。

## どう替えたか（パイプごと）

達人側の答えは3件とも一致している。
Homebrew は5分間隔のgit配信が潰れて **JSON配信へ**、CocoaPods は GitHub に CPU 制限をかけられて **CDNへ**、
cargo は git インデックスをやめて **sparse index へ**。全部「**配信の道を、作業の道から外す**」という同じ一手。

ここでも同じことをした。

1. **配信専用の枝 `gh-pages` を1本立てた。**
2. **書き手は `tools/pages_publish.sh` ただ1本**（Mac常駐）。
   履歴を常に**1コミットに固定**して毎回 force push する。
   → 書き手が1人・履歴1コミット・毎回force なので、**「向こうが先で合流できない」が原理的に起きない。**
3. `pages.yml` は `gh-pages` への push でだけ走るようにした。**main への push では配信の便が走らない。**
4. `machine_status_push.sh` から**写しの commit を丸ごと外した**。
   さらに「最後に push できた地点から HEAD が1歩も動いていなければ **main に一切触らない**」ようにした。

結果、**機械は main に書かない。main は人間の作業だけの道に戻った。**

## 載せているもの（ここが事故の分かれ目）

`gh-pages` に載るのは次の2つ**だけ**。

1. main が追跡しているファイル（`git archive` なので**追跡外の置きっぱなしは原理的に入らない**）
2. `status/public/` の生きた中身

作業ディレクトリを `git add -A` で丸ごと拾う形は**作っていない**。
（ツイート47,011件を誤って公開した事故は「`share/` を丸ごと add していた」ため。同じ形を二度と作らない）

`status/public/` には毎回さらに関所を掛けている。
1MB超・`.env` / `*.pem` / `*key*` / `*token*` / `*secret*` / `id_rsa` は名前で弾く。
**載せた顔ぶれは毎回 `status/pages_publish_files.txt` に書き出す**ので、後から目で確かめられる。
切り替え時に外したものは **0件**（＝今まで公開されていたものと同じ72ファイル）。

## 途中で踏んだ穴（同じ穴を二度踏まないために）

- **681MBを毎回まるごと展開すると3分以上かかる。** → `.git/lastmain` に前回地点を覚えて、**差分だけ**映すようにした。2回目以降は一瞬。
- **push が落ちた後、「中身に変化が無い」だけで次の周回が抜けてしまい、配信が古いまま生き続けた。**
  画面は真っ白にならないので気づきにくい＝一番たちが悪い壊れ方。
  → 手元と `refs/remotes/origin/gh-pages` を比べ、**向こうが遅れていたら中身に変化が無くても必ず押し直す**ようにした。3回まで粘る。
- **push 成功後に `refs/remotes/origin/gh-pages` を書き戻さないと、git は「向こうは何も持っていない」と思い込んで毎回600MBを上げ直し、回線が落ちる。** → `git update-ref` を入れた。
- **`git add` は `.gitignore` に従うので、公開したいものが黙って落ちる**（実測：`status/fact_source_baseline.json`）。→ `--force` を付けた。
- **`github-pages` 環境に「main からしか配信できない」枝しばりがあった。** → `gh-pages` を追加登録した。**main は残してある＝いつでも元へ戻せる。**

## 元へ戻したくなったら（1手）

`.github/workflows/pages.yml` の `branches: [gh-pages]` を `[main]` に戻して main へ push するだけ。
`github-pages` 環境の枝しばりには main を残してあるので、そのまま元の配信に戻る。

## ★残っている1点（次にやる人へ・まだやっていない）

`status/public/` は**まだ main に追跡されたまま**。しかし機械はもうそこを commit しないので、
main 側の写しは 2026-09-20 00:14 で凍っている。
このため **`git pull` のたびに、生きている `status/public/*.json` が古い内容で一瞬上書きされる**
（00:54 に実測：工場側 00:14 / 配信側 00:34 という逆転が起きた）。
5分便の `cp` ループが次の周回で必ず書き戻すので**1分以内に自然に治る**し、
画面が真っ白になることは無い。が、気持ちの悪い揺れなので根元を止めるべき。

直し方（**検証の時間を取れるときに**やること。中途半端にやらない）：

1. `git rm -r --cached status/public` で追跡から外す
2. `.gitignore` を書き換える。CI（`deliver-verify.yml` / `top-measure.yml`）が main へ書き戻す
   3ファイルだけは追跡を残す：

   ```
   status/*
   !status/public
   status/public/*
   !status/public/deliver_verified.json
   !status/public/top_measure.json
   !status/public/top_bytes.json
   ```

3. 配信には影響しない（`gh-pages` は `status/public/` を**丸ごと rsync で**映しているので、
   main が追跡しているかどうかと無関係）。切り替え後に必ず
   `https://tamago2022.github.io/tamago-shinchoku/status/public/top_status.json` を叩いて
   200 と中の時刻を確かめること。

## 触るときの注意

- ログは `status/pages_publish.log`。載せた顔ぶれは `status/pages_publish_files.txt`。
