## 1. 想定する最初の機能（店主の発言そのまま）

> あるWebサイトのURLを渡すと、専門用語を使わずに（AIという言葉も極力使わず）、
> そのサイトの改善点（写真、説明文、予約/問い合わせ導線など）を1〜2点、
> 優しい言葉で提案してくれる、シンプルな診断ツール。

## 2. 誰のためのツールか（Win-Winの一文）

- 対象：自分のお店・サービスのサイトを持っているが、何を直せば良いか分からない個人事業主。
- 失っているもの：予約・問い合わせの機会（サイトの写真が暗い、説明文が読みにくい、
  予約ボタンが目立たない等が原因で離脱されている）。
- 変わること：専門用語無しで「ここを直すと良い」が1〜2点だけ分かり、
  直すかどうかは本人が決められる（押し売りしない）。

## 3. 全体の流れ（パイプライン）

```
URL入力
  → ① 取得（HTML本文・画像・メタ情報を取る）
  → ② 機械チェック（ルールベース：画像・説明文・導線の有無をチェック）
  → ③ 言い換え（チェック結果を、優しい日本語の1〜2点の提案文に変換）
  → ④ 出力（シンプルな文章。専門用語・「AI」という語を使わない）
```

## 4. 技術方針（オリジナルで作らない・公式・実例に倣う）

  が既に実践している文体ルール（枷7・枷18＝短く・専門用語を避ける・弱い言い換えをしない）を流用する。
  新しいプロンプト設計を発明しない。
- **実例**：GTmetrix・Hotjar等の既存サイト診断サービスも、裏側はLighthouse/PageSpeed系の指標を
  使い、結果を要約して見せる構成が共通（調査済み・票に記録）。
