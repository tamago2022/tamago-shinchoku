#881 ごきげん補給所 重さ監査（第1段・コード変更なし）

対象：joy-relief-station（ごきげん補給所）。今回はコードを1行も変えず、実測だけを行った。

発車時のヒント文には「coverGuide.ts 6MBがそのまま重さの犯人」とあったが、実際は大半のページで既に解消済み（過去の複数セッションの修理・コミットf0e8ce43ほか）。ただし実ビルドを直接調べたところ、曲詳細ページ(room.card.$slug)と棚ページ(shelf.$worldId.$shelfId)の2つだけ、同じ修理が漏れていて今も静的importのままだった。これが今回の最重要発見（S級）。

過去に報告された重さ今の状態（実測）

A（大きい）

#原因現在の実装なぜ重い／危ないか修正方法改善予測副作用
A-1速さの回帰ガードがCIに未接続.github/workflows/quality-gate.ymlはビルド・仕入れ検品・YouTube IDマップ検査のみ実行。npm run check:perfの呼び出しなしこのガードは過去に本番で実際に起きた重さ事故の再発防止用。ガード自身のコメントに「直した修理が別セッションの上書きで本番から消えた」実例が記録されている。CI未接続だと同じ事故（今回のS-1/S-2のような修理漏れ含む）が誰にも気づかれず本番に出続けるquality-gate.ymlのBuildステップに run: npm run check:perf -- --main を1行追加。あわせてS-1/S-2の2ファイルをルールに追加速度そのものは変わらない（監視の追加）。将来の重さ回帰を機械的に抑えるビルド時間+数百ms程度。文字列一致のため大規模リファクタ時はルール更新が必要
A-2全ページ共通の"index"チャンクが大きい実ビルド実測：index-rPhaV_qI.js = 3,031.58KB(minify)/1,288.25KB(gzip)。React/ReactDOM/TanStack Query/lucide-react等のベンダーコードで、ほぼ全チャンクから参照される低速回線・低メモリのiPhone Safariでは、どのページを開いても最初に1.29MBのJSを読み終えるまで画面が動かない。「トップ白画面」の一因の疑いがあるが、LCP/TTIの実機計測はまだ行っていない（次段階の宿題）manualChunksでベンダーコードをさらに用途別に分割。使用頻度の低い管理者向けコンポーネントが混入していないか調査未検証（疑いの段階。次段階で計測してから数値を出す）チャンク分割を増やすとHTTPリクエスト数は増える（HTTP/2下では影響小）
A-3「一押し」バッジ画像が圧縮・リサイズされていないpublic/badges/concierge-pick.png が2,588.1KB(1536×1024px)。表示先ConciergePickBadge.tsxでは32〜40px角の小バッジとして使用（コメントに「短辺の15〜20%以下」と明記）loading="lazy"は付いているが、表示サイズの40倍近い解像度の画像をそのまま配信・デコードしている。「一押し」カードが複数並ぶページでは1枚あたり2.6MBが積み重なる実表示サイズ（32〜40px角）に十分な解像度までリサイズしてPNG/WebPで再書き出し該当画像1枚あたり-2.5MB程度（一般的なリサイズ+圧縮で数十KBまで削減可能な見込み）見た目の解像度は下がるが表示サイズが小さいため体感差はほぼ無い見込み。ロゴ等で複数箇所から参照されていないか確認要

B（中程度）

#原因現在の実装なぜ重いか修正方法改善予測副作用
B-1音楽の扉ページのDOM要素数そのものが多い実測記録(styles.cssコメント)：1ページにDOM要素25,855個・img要素1,711個・リンク1,780本。content-visibility:autoはスクロール中の計算コストは下げるが、DOM要素自体は開いた瞬間に全部生成される(消えない)低メモリのiPhone Safariでは、DOM要素数の多さ自体がメモリ確保・GCの負担になる。店主が報告している「スマホ操作時のクラッシュ／固まり」との直接の因果は未確定（次段階で実機検証が必要）棚単位のvirtualization(react-window等)導入、または「最初は上位N棚だけ描画しスクロールに応じて追加生成」する段階的レンダリング未検証。DOMノード数・メモリ確保量を数分の一に減らせる可能性はあるが、スクロール復元(scrollMemory.ts)やCtrl+F検索性への影響を検証しながら進める必要あり実装難度は中〜高。既存のスクロール位置復元・検索性を壊さない設計が必須。今回の監査範囲では最も慎重な検証が要る項目
B-2棚ページのカード一覧が件数無制限shelf.$worldId.$shelfId.tsxの cards.map(...) に上限なし。worlds.tsのgetVisibleShelfCards()にもslice/limitなし。ただし各行のサムネはimg loading="lazy"済みで画像の即時ダウンロードは発生しない大きい棚を開くとDOM行数がそのまま増える(B-1と同系統の問題)1ページの表示件数に上限を設け、以降はページング/もっと見るボタンにする未検証「全曲一覧で見たい」という利用シーンがあれば体験が変わるため、上限値の設計は要検討
B-3VideoCard.tsxにShelfCardViewと同型の未修理コードが残存VideoCard.tsx:409-410 window.addEventListener("gokigen:card-rewritten", onRewritten) をコンポーネント1枚ごとに直接張っている（cleanupはあるため真のメモリリークではない）。ShelfCardView.tsxは既にこれを単一hub方式に修理済みVideoCardが同時に多数マウントされるページ(room.*ページのvideos.map等)で、書き換え通知のたびに全インスタンス分のハンドラが走る。今回grepした範囲では1ページ数本程度でShelfCardViewの「数百枚」ほどの規模ではないが、動画本数が増えると再燃しうるShelfCardView.tsxと同じ単一hub方式(subscribeRewrite相当)へ統一する未検証(現状件数では体感差は小さい見込み。将来の予防措置)リスク小。既存のリライト通知の到達範囲を変えないよう注意
B-4管理画面向けサーバー関数にselect("*")＋limitなしadminShelves.functions.ts / inventory.functions.ts / adminTodos.functions.ts / coverGuideAdmin.functions.ts等、計10〜11箇所。いずれも管理画面専用で一般来訪者の経路ではない現在の件数では致命傷ではなさそうだが、データが増え続ける前提だと将来的に管理画面が重くなる各箇所にlimit/rangeを追加し、必要なカラムだけ取得する現時点では体感差はほぼ無い見込み(未計測)。データ増加への予防措置としての価値が主管理画面側にページングUIが必要になる分、実装コストはやや掛かる。一般ユーザー体験には影響なし
B-5曲詳細ページでReactのhydrationエラーが実際に出ている（追加発見）本番の曲詳細ページ/room/card/ado-kawaikute-gomenを実ブラウザ(headless Chrome)で開き自動クリック検査したところ、コンソールにMinified React error #418（サーバー側で生成したHTMLとクライアント側の再描画結果が一致しない＝hydration mismatch）を1件検出。同じ検査を本番トップ・棚ページ(kattemi-yokatta)では実行し0件だったため、このページ種別（曲詳細ページ）またはこの曲固有の問題の疑いhydration失敗はReactがサーバー出力を一度捨ててクライアント側で丸ごと再描画し直す動作を招く。低メモリ端末では追加の再計算コストになり、店主が報告している「動画再生後フリーズ」「画面遷移の引っ掛かり」との因果は未確定だが疑いの一つとして記録する次段階で該当ページのSSR出力とクライアント初期描画のdiffを取り、日時・件数など環境依存な値がSSR/CSRで食い違っていないか調査する未検証（原因未特定のため見積もり不可。次段階の調査対象）調査のみでは副作用なし

C（軽微）

#原因現在の実装なぜ軽微か修正方法改善予測副作用
C-1静的アセットの明示的キャッシュ戦略(_headers/Service Worker等)がリポジトリ内に無いリポジトリ内に_headersファイルやService Worker実装は見つからない(Viteの既定挙動のまま)Viteのcontent-hashファイル名は「同じ内容なら同じURLに一生涯留まる」設計のため、多くのホスティングはデフォルトで長期キャッシュを返す。実害は未実測次段階でLovable本番のResponse Headersをcurl -Iで実測し、弱ければ_headers等で明示指定する未計測（まず実測してから判断すべき項目）調査のみなら副作用なし。設定変更時はキャッシュ無効化のタイミング調整が必要

③ 確認済み・問題なし（実測して確認したもの）

  • YouTube埋め込み：一覧・カードは<img loading="lazy">のサムネイルのみを表示し、iframeは再生ボタンを押した時だけ生成（VideoCard.tsx実装を直接確認）
  • route単位のcode splitting：vite.config.tsでloader／component／pendingComponent／errorComponent／notFoundComponent すべてが分割対象（過去にloaderが漏れて8MBが混入した事故があり、修正済み）
  • 検索(search.tsx)はサーバー側で60件に上限済み。publicListArtistsも2000件上限済み
  • 公開ページ側のSupabase問い合わせにselect("*")＋limitなしは無し（該当は全て管理画面専用）
  • useMergedShelves.tsは世界(worldId)単位でクエリキー分割・staleTime5分でキャッシュ

④ 今回の実測で最も重さへの寄与が大きい上位3つ

  3. B-1：扉ページDOM 25,855個――低メモリ端末でのクラッシュ疑いの最有力候補（要実機検証）
