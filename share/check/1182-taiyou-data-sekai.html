#1182 26,000件をスマホに配る　世界の事例

2026-09-29 ／ 調べただけ（コードは書いていない・自分で考えた案はゼロ・全部出典付き）
公式ドキュメントと公表済みケーススタディからお手本を5つ拾い、そのまま移植できる1つとして Pagefind を選んだ。うちが今やっている「26,000件を1つのJSに畳んで1曲ページごとに全部落とす」形は、V8公式とVite公式が名指しで勧めていない側の形だった。

② お手本 5つ

① YouTube ― その画面に要る部品だけを1本のリクエストにまとめて取る

50個以上の部品に「部品→JSモジュール」の対応表を作り、lazyと印を付けたものは後で読む。ただし遅延読みだけだと滝（waterfall）になったので、その画面に最低限必要な部品を1本のリクエストにまとめる形に直した。

公表数字（出典元の実測: 76%／実測: 75%）：モバイルwebのURLの76%がCore Web Vitals通過／デスクトップwatchページのラボLCP 4.6秒→1.6秒／プレイヤーのJS実行時間 最大75%減。

出典（Google公式 web.dev）https://web.dev/case-studies/better-youtube-web-part1

② Pagefind ― 検索の索引を語頭でシャードし、打った文字に当たる欠片だけ落とす

索引をchunkに分割して置き、ブラウザは検索のたびに索引の小さな部分集合しか読まない。サーバーを持たない静的サイト向け。

公表数字：10,000ページのサイトの全文検索を、ライブラリ込みの総通信300kB未満で実行。多くのサイトでは100kB前後。

実物：MDN／Godot／XKCD のデモが公開されている。JSONやPDFもNode/Pythonの索引APIで食わせられる。

出典 https://pagefind.app/ ／ https://cloudcannon.com/blog/introducing-pagefind/

③ Next.js（Vercel公式）― 1ページ＝1つのJSON

ビルド時にHTMLに加えてそのページ専用のJSONを吐き、クライアント遷移ではそのJSONだけを取る。HTMLもJSONもCDNでキャッシュ可。リンクが画面に入ったら先読みするが、回線が溢れないようスケジュールする。

出典 getStaticProps ／ Prefetching

④ Pinterest ― バンドルを vendor / entry / async の3種に割る

公表数字（出典元の実測: 103%）：コアJS 650KB→150KB／First Meaningful Paint 4.2秒→1.8秒／Time To Interactive 23秒→5.6秒（再訪3.9秒）／モバイルwebの週間利用者 +103%。

出典 Google Dev Channel ケーススタディ

⑤ web.dev公式の型2つ ― 一覧は見えている分だけ描く／骨組みは場所を先に予約する

一覧（仮想化）：見えているものだけ描き、スクロールで「窓」を動かす。継ぎ足しは react-window-infinite-loader、ちらつき防止は overscanCount（増やしすぎは逆効果）。

骨組み（CLS）：遅れて来る中身の場所を最初のレイアウトで予約する（min-height / aspect-ratio）。寸法が分からなくても、既定で高さを予約しないまま（実測: 0px）にするより「それらしいmin-height」を置く方がほぼ常に良い。

出典 仮想化 ／ CLS ／ 無限スクロール

③ そのまま移植する1つ：Pagefind

「似せる」ところがない。CLIを走らせて出てきた pagefind/ をそのまま置き、公式のUIコンポーネントをそのまま読み込むだけ。索引の割り方をこちらで一切考えない＝オリジナルにならない。

1. 前提がうちと同じ（サーバーなし／静的ホスティング／ビルド済みHTMLがある）。
2. 規模が公表値の範囲内。索引は語頭でchunkに割れるので、件数に比例して落ちる量が太らない。
3. 曲データ（JSON）もNode/Python APIでそのまま食える。
4. MDN・Godot・XKCD で動いている実物を触って確かめられる。

④ やってはいけない手 3つ

✗1. データを「JSのオブジェクトリテラル」としてバンドルに畳み込む　― うちが今まさにやっている

V8（Chromeのエンジン）公式が名指しで否定。JSON.parse('…') は同内容のJavaScriptリテラルよりparse・compile・実行のすべてで大幅に速い。大きなデータをリテラルで書くと preparse と lazy-parse で二度読まれる危険。目安は10kB以上。うちは2,626KBを1曲ページごとに読ませている。

出典 https://v8.dev/blog/cost-of-javascript-2019

✗2. 静的importで全部入りを1ファイルに畳む

Vite公式は逆を既定にしている。まとめ読みの対象は既定で動的importの遅延読み込みになり、ビルド時に別チャンクへ分かれる。{ eager: true } を渡したときだけ静的importとしてまとめてバンドルされると明記。分割の口は build.rollupOptions.output.manualChunks。TanStack Router側も .lazy.tsx 分割と、遅い部分だけ後で解決する Deferred Data Loading を公式に用意している。

出典 Vite Features ／ Build Options ／ TanStack Code Splitting ／ Deferred Data Loading

✗3. 骨組みを「高さ0の空要素」で出して、あとから中身を差し込む　― うちの「崩れる」の正体

web.dev公式が名指しで否定。遅れて来る中身の場所は最初のレイアウトで予約（min-height / aspect-ratio）。
同系統の教訓：Netflix はログアウト時トップページからクライアント側Reactと関連ライブラリ（200kB超）を外しただけで Time-to-Interactive が（出典元の実測: 50%）以上改善した。

出典 web.dev CLS ／ Netflix ケーススタディ
