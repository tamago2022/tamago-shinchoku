#687 status/丸ごとロールバック事故・真因と復旧

2026-09-13 実測。当初「queue.jsonだけの問題」と見誤っていたが、たまごさんの指摘で調べ直し、git層の真因を特定・修理した。
調査の途中経過（正直に書く）：最初の対応（下記③）はアプリ層の鍵（queue_lock）だけを直し、queue.jsonをtranscriptから手作業で復元した。しかしその後、同じ事故がさらに発生し、その復元分ごと再度消えた（289件→264件・776番は3回別内容に上書き）。原因はqueue.jsonの中ではなく、もっと下のgit層にあった。

① 真因：git pull --rebase が status/ を丸ごと巻き戻していた

tools/machine_status_push.sh（5分おき）とtools/command_watch.sh（30秒おき）の両方に、 git commit ... || true; git pull --rebase -q ... || true; git push ...という同一パターンがあった。

実測したメカニズム：未コミットの変更が残っている状態でpull --rebaseが走ると、gitが自動でそれらをautostashへ退避する。rebase自体が何らかの理由で完走できず失敗すると（|| trueが握りつぶすため誰にも気づかれない）、作業ツリーは古いorigin/mainの内容へサイレントに巻き戻り、autostashは二度とpopされずに残る。

この事故は今日が初めてではなかった：git fsck --danglingで見つかったautostash残骸だけで、2026-09-02〜09-12の間に12回発生していたことを確認した（今回初めて実害＝番号の消失として顕在化した）。

③ 修理の中身

対策内容状態
rebase→mergeへ変更machine_status_push.sh・command_watch.shのpull --rebaseをpull --no-rebaseに変更。mergeが失敗してもコンフリクト状態で残るだけで、rebaseのautostashのようにサイレントに巻き戻ることが無い構造にしたcommit済み
自己修復周回開始時に壊れたrebase/merge残骸（.git/rebase-merge等）を検知したら自動で片付けてから進む。pullが失敗したら黙って続けずmerge --abortで必ず元へ戻し、status/git_rebase_incidents.logへ記録するcommit済み

永久保全1回目の事故直後のautostashコミットにgit tag rescue-687-autostash-20260913を付け、gcで消えないようにした実施

⑥ 正直な限界（隠さず書く）

・queue.json以外の「done」履歴（進捗表に一度出た完了記録）が、今回の複数回のロールバックで一部失われている可能性がある。実際に本番に出た成果物そのものは無事（GitHub Pages・Lovable本番は別途pushされているため）だが、queue.json内の「いつ誰が何をdoneにしたか」の記録が一部欠落している可能性は残る。全件の追跡はしていない。
・rebase→merge化で今回の型の事故は防げるはずだが、mergeでもコンフリクトが起きた場合は人の目での解消が必要になる場合がある（サイレントな巻き戻りは無くなったが、コンフリクトの発生自体は無くならない）。
・777〜781番は今回意図的に触っていない（既に別セッションが再作成し稼働中のため）。念のため内容の重複が無いか、後で1回だけ目視確認をお勧めする。
